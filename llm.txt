# tael — LLM usage notes

Context for agents using the `tael` CLI or querying a tael server.
Covers the command surface, the HTTP query surface, and the known
limits — so you don't generate calls that silently fail or return
misleading results.

## CLI quickstart

`tael` is a thin client over the tael server's REST API. Default server
is `http://127.0.0.1:7701`; override with `--server <url>` or, for a
localhost-only shorthand, `--port-rest <N>`.

Global flags (must appear before or after the subcommand, not nested):
- `--server <url>` — server base URL
- `--port-rest <N>` — shorthand for `--server http://127.0.0.1:<N>`. For
  `tael serve`, sets the REST API listen port instead. Conflicts with
  `--server`.
- `--port-otel <N>` — (serve only) OTLP gRPC ingest port on 127.0.0.1.
  Ignored by client commands.
- `--format json|table` — output format, default `json`. Prefer `json`
  for machine parsing; `table` is for humans.

`tael serve` stores telemetry under `~/.tael/data` by default and its WAL under
`~/.tael/wal_files`; override with `--data-dir`/`TAEL_DATA_DIR` and
`--wal-dir`/`TAEL_WAL_DIR`.

### Querying data

```
tael query traces [flags]
tael query logs    [flags]
tael query metrics [flags]
```

**Traces** — filter spans:
- `--service <name>`         exact service match
- `--operation <substr>`     substring match on span operation
- `--min-duration <dur>`     e.g. `100ms`, `1s`, `500` (bare number = ms)
- `--max-duration <dur>`
- `--status ok|error|unset`
- `--last <dur>`             window, e.g. `5m`, `1h`, `24h`, `7d`
- `--limit <n>`              default 100

Example: `tael query traces --service api --status error --last 15m`

**Logs** — filter log records:
- `--service <name>`
- `--severity trace|debug|info|warn|error|fatal`
- `--body-contains <substr>`  substring, **not** regex
- `--trace-id <id>`           exact match (find logs attached to a trace)
- `--last <dur>`
- `--limit <n>`               default 100

Example: `tael query logs --severity error --last 1h --body-contains timeout`

**Metrics** — two modes:

*Filter mode* (simpler, recommended for most agent use cases):
- `--service <name>`
- `--name <metric_name>`      exact match
- `--type gauge|sum|histogram|summary`  (will not match remote-write data)
- `--last <dur>`
- `--limit <n>`               default 500

*PromQL mode* — set `--query`; the filter flags above are ignored
except `--last`:
- `--query "<expr>"`          PromQL subset (see section below)
- `--last <dur>`              lookback for bare selectors; `rate()` uses
                              its own `[...]` bracket instead

Examples:
```
tael query metrics --name http_requests --service api --last 5m
tael query metrics --query 'rate(http_requests{service="api"}[5m])'
tael query metrics --query 'sum by (service) (http_requests)'
```

### Fetching a full trace

```
tael get trace <trace_id>
```

Returns every span in the trace, ordered by start time. Use this after
`tael query traces` finds something interesting.

### Services

```
tael services
```

Lists every service that has emitted spans, with span count, trace
count, average span duration, and error rate. Good starting point for
exploration when you don't know what services exist.

### Comments on traces

Persistent annotations attached to a trace (or a specific span) — used
by agents to leave notes across sessions.

```
tael comment add <trace_id> "<body>" [--author <name>] [--span-id <id>]
tael comment list <trace_id>
```

### Live / TUI

```
tael live [--service <name>] [--status <s>] [--interval <secs>]
tael live --evals
tael live --eval-run <run_id>
```

Interactive ratatui feed of incoming spans. Primarily a human tool — not
useful from an agent. Skip unless explicitly asked.

### Evals

Eval support reuses existing telemetry: spans carry `tael.eval.*`
attributes, scores are `tael_eval_score` metric points, and notes are trace
comments.

```
tael eval run <cases.jsonl> --suite <name> --cmd '<command with {case_id}>'
tael eval score <run_id> <scores.jsonl>
tael eval runs
tael eval status <run_id>
tael eval cases <run_id>
tael eval scores <run_id>
tael eval report <run_id>
tael eval compare <run_id> <baseline_run_id>
```

Score JSONL lines require `case_id`, `metric`, and `value`; `run_id` is filled
from the command argument when omitted. Optional fields include `suite_id`,
`trace_id`, `span_id`, `scorer`, `label`, `rationale_sha256`, and `source`.

### Attribute filters and text search

```
tael query traces --attribute http.method=GET            # exact
tael query traces --attribute 'http.route~=/users'       # substring
tael query traces --attribute 'gen_ai.request.model=~claude-.*'   # regex
tael query traces --text PaymentDeclined
```

Attribute filters are repeatable and ANDed. An invalid regex is rejected with
a 400 (CLI exit 3) rather than silently matching nothing.

`--text` searches a Tantivy index over three kinds of text, all resolving to
trace IDs so one query reaches every signal:
- LLM prompt/completion payloads
- log bodies (only for logs carrying a trace ID)
- span attribute values, flattened to `key=value` text and truncated at 4 KB
  per span

Requires `tael-backend` storage; under `--storage duckdb` it returns nothing.

### Eval case suites

```
tael eval suite push <name> cases.jsonl     # whole-set replace
tael eval suite pull <name>[@<snapshot>] [--out FILE]
tael eval suite snapshot <name> [--note "..."]
tael eval suite list
tael eval suite diff <ref> <ref>            # ref = name or name@snapshot
```

The server becomes the system of record while JSONL stays the interchange
format, so suites can still live in git. A case is stored as a
content-addressed blob and a snapshot is an ordered list of hashes, so
unchanged cases are shared rather than copied and diffing is a set operation.

`push` replaces the working set — a case omitted from the file is removed,
because a merge-only push makes deleting a stale case impossible.

A snapshot id is derived from content, so re-snapshotting an unchanged suite
returns the same id instead of accumulating duplicates. Pin a run to a
snapshot (`name@snap_...`) so two experiments provably compared the same data.

`pull` emits canonical JSONL (object keys sorted), so a push/pull round trip
is byte-stable and reformatting a file is not mistaken for editing every case.

`diff` reports an edited case as `changed`, not as an add plus a remove — it
is still the same case.

### Structure and comparison

```
tael topology --last 1h
tael diff --last 10m --baseline 1h [--service NAME]
tael get metric <name> --last 24h
```

`topology` reconstructs the service dependency graph from span parent/child
edges — it reflects what the system actually did, not a declared architecture.
Cross-service edges only; same-service parent/child pairs are internal
structure. `spans_with_parent_outside_window` counts spans whose parent fell
outside the window, so a high value means the graph is missing edges and the
window should be widened.

`diff` is the unopinionated sibling of `anomalies`: every summary metric with
current, baseline, delta, and ratio, with no threshold applied. The baseline
window *contains* the current one, so rates compare directly but totals do not
— the response says so and reports both.

`get metric` describes one metric before you query it: type, unit, label keys,
series count, value range, and whether the points retained histogram buckets
(which decides whether `histogram_quantile` will work on it).

### Alerts

```
tael alert create --name high-errors \
  --query 'tael:span_error_rate{service="api"} > 0.05' \
  --for 5m --sink webhook=https://... --sink exec='./page.sh'
tael alert list
tael alert delete <name>
tael alerts [--limit N] [--follow]
```

Rules evaluate a PromQL-subset expression every 30s and emit an event on state
transition only — a rule firing for an hour does not re-deliver. `--for`
requires the condition to hold *continuously*; a dip resets the streak.

These span-derived series exist without any metric instrumentation, each
labelled by `service` (plus a fleet-wide aggregate under `service="tael"`):
`tael:span_error_rate`, `tael:span_p95_ms`, `tael:span_p99_ms`,
`tael:span_count`, `tael:span_error_count`.

`tael alerts --follow` blocks and streams — it is the long-poll primitive for
waiting on a system rather than polling it.

### Online scoring

```
tael score rule create --name faithfulness --sample 0.05 \
  --match service=agent-api --match attribute:gen_ai.system=anthropic \
  --cmd ./judge.sh
tael score rule list
tael score rule delete <name>
```

Samples matching production traces and runs the scorer once per trace, writing
results as `tael_eval_score` points tagged `source=online` and `rule=<name>`.
The scorer sees `TAEL_EVAL_TRACE_ID`, `TAEL_EVAL_SPAN_ID`, `TAEL_EVAL_SERVICE`,
`TAEL_EVAL_OPERATION`, `TAEL_EVAL_RULE`, `TAEL_EVAL_ONLINE=1`, and must print
one JSON object per line with `metric` and `value` (optionally `rationale`).
Same contract as `tael eval run`, so one script works in both places.

Sampling is deterministic in the trace ID, so a given trace is always in or out
of the sample. `score rule list` reports traces seen vs sampled and the last
scorer error — a silently broken judge shows up as `failures`, not as missing
data.

### Config and keys

```
tael config show [--data-dir DIR]
tael config init [--force]
tael auth create-key --name NAME --role reader|writer|admin
tael auth list
tael auth revoke <key-id>
```

Retention defaults to 365 days for every signal; `config init` writes the
shorter recommended per-signal windows. Precedence is flag > env > file >
default.

### Output parsing notes

With `--format json` (default), responses have these top-level shapes:
- `tael query traces` → `{"spans": [...]}`
- `tael get trace` → `{"trace_id", "span_count", "spans": [...]}`
- `tael services` → `{"services": [...]}`
- `tael query logs` → `{"logs": [...], "count": N}`
- `tael query metrics` (filter mode) → `{"metrics": [...], "count": N}`
- `tael query metrics --query` → `{"query", "series": [...], "count": N}`
- `tael comment list` → `{"comments": [...], "count": N}`
- `tael eval runs` → `{"runs": [...], "count": N}`
- `tael eval status` → `{"run": {...}}`
- `tael eval cases` → `{"run_id", "cases": [...], "count": N}`
- `tael eval scores` → `{"run_id", "scores": [...], "count": N}`
- `tael topology` → `{"services": [...], "edges": [...], "spans_examined", "spans_with_parent_outside_window"}`
- `tael diff` → `{"current_window_seconds", "baseline_window_seconds", "<metric>": {"current","baseline","delta","ratio"}, "totals", "note"}`
- `tael get metric` → `{"metric","type","unit","point_count","series_count","services","label_keys","value_min","value_max","histogram_quantile_available","recent_points"}`
- `tael alert list` → `{"alerts": [...], "count": N}`
- `tael alerts` → `{"events": [...], "count": N}`
- `tael score rule list` → `{"rules": [...], "count": N}`
- `tael config show` → `{"config_file","config_file_exists","storage","retention_days"}`
- `tael auth list` → `{"keystore","count","keys": [...]}`

Errors are returned as `{"error": "..."}` with a non-2xx HTTP status.

### Exit codes

Every command exits with a category code, so a caller can branch without
parsing output:

```
0  success
1  unclassified failure
2  query succeeded but matched nothing
3  malformed query, filter, or argument
4  server unreachable
5  authentication or authorization failure
6  a --exit-on condition tripped (tael watch)
```

Code 2 is not an error — the command still printed a well-formed empty
response. Failures also print `{"error", "category", "exit_code"}` on stderr.

### Blocking on a condition

```
tael watch --last 1m --interval 10 \
  --exit-on 'error_rate>0.05' --exit-on 'p95_ms>2x' [--max-ticks N]
```

Polls and prints deltas until a condition holds, then exits 6 with a verdict
naming what tripped. Thresholds are absolute (`error_rate>0.05`) or relative to
the first sample (`p95_ms>2x`), which is what you want when starting mid-incident
with no known-good baseline. Fields resolve flat (`error_rate`) or dotted
(`traces.error_rate`). Without `--exit-on` it polls forever, as before.

### Explaining a query

`tael query traces --explain` adds an `explain` object: `access_path`,
`tiers_consulted`, `rows_scanned`, `rows_returned`, `limit_reached`,
`effective_filters`, `elapsed_ms`, and `notes` describing the mistakes that
actually produce confusing results (silently hitting the row limit,
exact-match attribute filters, an unbounded window).

## PromQL subset (`GET /api/v1/metrics/query?query=...&last=...`)

The server implements a **small hand-rolled PromQL-ish parser**, not real
PromQL. Stick to the grammar below.

### Supported

- Bare selector:       `metric_name`
- Labelled selector:   `metric_name{label="value", other!="x"}`
- Rate over range:     `rate(metric_name{...}[5m])`
- Aggregators:         `sum|avg|min|max|count(expr)`
                       `sum by (label1,label2) (expr)`
                       `sum(expr) by (label1,label2)`
- Duration units:      `s`, `m`, `h`, `d`
- Synthetic labels:    `service` (maps to the resource service name),
                       `__name__` (maps to the metric name)
- `last=` query param: lookback window for bare selectors (default 5m).
                       Ignored for `rate()`, which uses its own bracket.

### NOT supported — will fail to parse or produce wrong results

- Binary operators between series: `a / b`, `a + b`, comparisons, `and/or/unless`
- `without (...)` clauses — only `by (...)` is recognized
- Regex matchers: `=~`, `!~` (only `=` and `!=` work)
- Offset modifier: `metric offset 1h`
- Subqueries: `rate(metric[5m:1m])`
- Range queries / `/api/v1/query_range` — all evaluation is **instant**
- `topk`, `bottomk`, `quantile`, `stddev`, `stdvar`
- Scalar literals, `vector()`, `time()`, `timestamp()`
- `@` modifier, `absent()`, label_replace/label_join
- Nested binary ops or arithmetic inside aggregators

### Rate semantics caveat

`rate(sel[dur])` computes `max(last - first, 0) / elapsed_seconds` across
all samples in the window — a naive counter-reset clamp. This differs
from Prometheus, which extrapolates across scrape boundaries. Expect
small numerical drift vs. a real Prometheus server, especially on short
windows or sparse series. Good enough for trend detection; don't use it
for SLO math.

### Histogram metrics

OTLP Histogram and ExponentialHistogram data points retain their bucket
layout in a `histogram` object on the point:

    {"bounds": [10.0, 50.0, 100.0], "counts": [2, 5, 2, 1],
     "count": 10, "sum": 420.0, "min": 3.0, "max": 250.0,
     "temporality": "cumulative"}

`counts` is per-bucket (not cumulative) and always has one more entry
than `bounds`; the last entry counts observations above the final bound.
Exponential histograms are converted to explicit bounds at ingest, so
there is one shape to query regardless of how the client encoded it.

Query percentiles with the PromQL subset:

    histogram_quantile(0.95, http.server.duration)
    histogram_quantile(0.99, http.server.duration) by (service)

Unlike Prometheus, the second argument is the metric selector itself —
there are no `le`-labelled `_bucket` series to rate over.

Caveats:
- The result interpolates linearly within the containing bucket, so it
  is bucket-resolution accurate, not exact.
- A quantile falling in the open-ended top bucket reports the producer's
  `max` (or the last bound when `max` is absent).
- `temporality` decides how points combine over the lookback window:
  `delta` points are summed, `cumulative` points already contain every
  earlier observation so only the newest is used.
- Points with no bucket layout (pre-retention rows, remote-write data,
  the legacy DuckDB backend) produce **no series** rather than a zero.
- Merging across a `by (...)` grouping requires identical bounds;
  mismatched layouts are skipped, not approximated.

## Prometheus remote-write (`POST /api/v1/write`)

- Accepts Prometheus remote-write v1: Snappy-compressed protobuf body.
- Label mapping: `__name__` → metric name; `service.name` or `job` →
  service; everything else → attributes.
- Remote-write v1 carries no type information, so every ingested point
  is stored with `metric_type = "unknown"`. Queries filtering by
  `--type gauge` etc. will not match remote-write data.
- `NaN` samples (Prometheus "stale" markers) are dropped on ingest.
- No metadata handling, no exemplars, no native histograms. Remote-write
  flattens histograms into `_bucket`/`_sum`/`_count` series before the
  wire, so there is no bucket layout to retain and `histogram_quantile`
  does not apply to remote-write data.

## Datadog trace-agent intake (`/v0.3|/v0.4|/v0.5/traces`, `GET /info`)

- `tael serve` listens on the Datadog agent's default port
  (`127.0.0.1:8126`) by default, so dd-trace clients work with zero
  configuration. Move or disable it with `--dd-agent-addr <addr|off>` /
  `TAEL_DD_AGENT_ADDR`. If the port is already taken (a real Datadog
  agent), tael warns and keeps running without the dedicated listener.
- The same endpoints are also mounted on the REST listener; pointing a
  service explicitly with `DD_TRACE_AGENT_URL=http://127.0.0.1:7701`
  (or `unix://<socket>`) works too.
- v0.3/v0.4 accept msgpack (default) or JSON payloads; v0.5 accepts the
  msgpack string-table format. `GET /info` advertises these so clients
  negotiate a supported version.
- Mapping: `meta` and `metrics` tags → span attributes; `resource` →
  `resource.name` attribute; `type` → `span.type` attribute; `error` →
  span status; `span.kind` meta tag → span kind; `name` → operation.
  64-bit trace ids are widened to 128-bit using the `_dd.p.tid` tag.
- `gen_ai.*` tags in `meta` get the same typed-LLM promotion as OTLP.
- Client stats (`/v0.6/stats`) and telemetry (`/telemetry/proxy/*`) are
  accepted and discarded. Remote config is not implemented (404), which
  clients handle by disabling it.

## Filter-mode metric query (`GET /api/v1/metrics`)

If you don't need PromQL, the simpler endpoint supports:
`service`, `name` (exact), `metric_type`, `last`, `limit`.
This is often more reliable for agents than constructing PromQL.

## Log query (`GET /api/v1/logs`)

Supports: `service`, `severity`, `body_contains` (substring, not regex),
`trace_id`, `last`, `limit`. No structured field querying beyond those —
attributes are stored as JSON but not indexed or queryable yet.

## Trace query (`GET /api/v1/traces`)

Supports: `service`, `operation` (substring), `min_duration_ms`,
`max_duration_ms`, `status` (`ok|error|unset`), `last`, `limit`. No
attribute filtering yet.

## General

- All timestamps returned are UTC ISO 8601.
- Default limits: traces/logs 100, metrics 500. Raise with `limit=`.
- The default storage engine is `tael-backend` (an LSM hot tier over a
  Parquet cold tier), not DuckDB. DuckDB is a legacy backend behind
  `--features duckdb`.
- `tael query sql` requires a build with the `duckdb` feature. On a default
  install it returns an error; use the filter commands, the PromQL subset,
  and `summarize`/`diff`/`topology` instead.
- `query_traces` has no secondary indexes: it walks the time index
  newest-first and deserializes every span until the limit fills, so a
  low-selectivity filter over a large window is the slow case. Prefer narrow
  `last=` windows. `summarize` is a full scan of its window — roughly 65ms
  per 10k spans — so bound it on a busy server.
- Auth is off by default when every listener is loopback. A server bound to
  a non-loopback address requires API keys and refuses to start without them
  (override with `--auth off`). Authenticate with
  `Authorization: Bearer <key>`; the CLI reads `TAEL_API_KEY` or `--api-key`.
- OTLP ingest accepts gRPC on :4317 and HTTP/protobuf on :4318. OTLP/JSON is
  not supported.
